# Iteration Log

Running log of real bugs hit during development and how they got fixed -
separate from `ARCHITECTURE.md`'s Decision Log (which is for design
choices, not bug fixes) and `bugs/BUG_REPORT.md` (which is for issues
found *in PGA's agent*, not our own code). This is evidence-of-iteration
material for the submission - what actually broke, not a polished retelling.

---

### 2026-08-18 — `ModuleNotFoundError: No module named 'audioop_lts'` on first bridge server run
- **What happened:** First attempt to run `uvicorn bridge.server:app --port 8000` failed on import, tracing into `bridge/recorder.py`'s `import audioop_lts as audioop` fallback.
- **Root cause:** Two things stacked. First, Python 3.13 (confirmed via the traceback path showing `python3.13`) removed the `audioop` module from the standard library entirely, which `recorder.py` already accounted for via a fallback import to the `audioop-lts` backport package. Second, that fallback package had been added to `requirements.txt` *after* the local venv was already created and `pip install` already run once - so the venv simply didn't have it yet.
- **Fix:** Re-ran `pip install -r requirements.txt` inside the existing venv to pick up the new dependency. No code changes needed - the code was already correct, the environment just needed to catch up.
- **Status:** fix applied (reinstalled dependencies); confirmation that the server now starts clean is still pending.

### 2026-08-19 — First real call connected, then OpenAI rejected `session.turn_detection`
- **What happened:** First fully end-to-end test call: Twilio fetched `/twiml` (200 OK), the media WebSocket connected, and the OpenAI Realtime session opened - but OpenAI immediately returned `invalid_request_error: Unknown parameter: 'session.turn_detection'`.
- **Root cause:** Placed `turn_detection` as a top-level field under `session` in the `session.update` payload. The current Realtime API schema nests it under `session.audio.input.turn_detection`, alongside `format` and `transcription` - an older API version had it at the top level, and the code was written against that.
- **Fix:** Moved `turn_detection` into `session.audio.input`, matching where `format` and `transcription` already lived (`bridge/server.py`).
- **Status:** fix applied; confirmation of a clean full call (audio actually flowing both ways) is still pending the next test call.

### 2026-08-19 — Bot hallucinated into Spanish on its first turn, then briefly spoke as if it were the agent
- **What happened:** In the first successful full call (CA2346562065db120c1382893a6c7e3538), PGA's agent opened in clean English ("This call may be recorded..."). Our patient bot's very first reply was entirely in Spanish, unprompted - nothing in the audio it heard was Spanish, and `DEFAULT_INSTRUCTIONS` never mentions Spanish. This knocked PGA's own IVR into its Spanish-language menu ("Para Español, oprima el 2"), which then itself cut off mid-sentence into English - a secondary effect worth remembering as a possible real PGA-side bug later, but not the root cause here. A related issue in the same call: one bot turn briefly spoke *as the office* ("gracias por llamar" - "thanks for calling") instead of staying in the patient role.
- **Root cause:** Language-drift hallucination from the Realtime model - a known failure mode when a voice model isn't explicitly pinned to one language and one role. `DEFAULT_INSTRUCTIONS` said what the persona wants but never said what language to use or reinforced which role it plays.
- **Fix:** Added explicit lines to `DEFAULT_INSTRUCTIONS`: always speak English regardless of what's heard, and always stay in the patient role, never the agent's.
- **Status:** fix applied; confirmation this actually prevents the drift is still pending the next test call - language hallucinations in voice models aren't always fully eliminated by a prompt instruction alone, so this is worth specifically re-testing for, not just assuming fixed.

### 2026-08-19 — The `audioop_lts` fallback import could never have worked (corrects the 2026-08-18 entry)
- **What happened:** A scratch script copying `recorder.py`'s `import audioop` / `except ImportError: import audioop_lts as audioop` pattern failed with `ModuleNotFoundError: No module named 'audioop_lts'` — *with* the fallback present. Checking the venv showed `audioop-lts` had also silently vanished from it again, so `recorder.py` itself was one import away from the same crash.
- **Root cause:** The package is named `audioop-lts`, but the module it installs is plain `audioop` — a drop-in for the removed stdlib name. `import audioop_lts` has never been a real module, so the fallback branch was dead code that could only ever re-raise a more confusing error. The 2026-08-18 entry's conclusion ("the code was already correct, the environment just needed to catch up") was wrong: installing the package makes the *first* import succeed, which is why the broken fallback was never exercised.
- **Fix:** `recorder.py` now has a single `import audioop` with an `except ImportError` that raises a clear install instruction instead of pretending there's a second module to try. Dependencies reinstalled.
- **Status:** fixed and verified — `recorder.py` imports cleanly, and the offline harness produced a mixed MP3 through the audioop path.

### 2026-08-19 — Barge-in gated on task-liveness would have silently never fired
- **What happened:** First run of the offline bridge harness (fake Twilio + fake OpenAI, real ElevenLabs): the scripted mid-playback `input_audio_buffer.speech_started` produced no `clear` message to Twilio. Barge-in — the piece the migration brief flagged as "most likely to feel wrong on the first attempt" — did nothing at all.
- **Root cause:** The handler only sent `clear` if the TTS playback task was still running. But ElevenLabs streams ~12x faster than realtime, so a 5-second reply is fully handed to Twilio in under half a second and the task exits — while the audio plays on from Twilio's buffer for seconds more. Exactly the window where a real barge-in happens is exactly the window where the task is already done.
- **Fix:** Send `clear` unconditionally on `speech_started` (and cancel any playback task that does happen to be alive). `clear` on an empty buffer is a no-op, so there is no cost when the bot wasn't talking.
- **Status:** fixed; harness now shows media → clear → next reply's media in order. Still needs confirming on a real call with genuine cross-talk — the `interrupting_caller` scenario exists to force that.

### 2026-08-19 — Crosstalk on a real call: extra unprompted bot turn, and a response that answered a question not yet asked
- **What happened:** First real call to Pretty Good AI's test line (`refill_controlled_substance`, CA828bba9caf4293b6501b925e0975b08a). Two things stood out on playback and in the transcript. First, right after the agent said "and your date of birth as May 14th, 1992? Is that correct? If so, please spell your first and last name for me," the bot's reply opened with "I don't have the phone number on file handy" — a question about a phone number the agent hadn't asked yet at that point in the transcript. Second, after the agent said "Transferring you now. Thank you," the bot produced two full replies back-to-back ("Hello, thanks for the transfer—I'll just wait...", immediately followed by "Hi, sorry about that. This is Tyler Brooks again...") with no agent line in between. The recording has audible overlap where both sides are talking at once.
- **Root cause (working theory):** `session.audio.input.turn_detection` was left at bare `{"type": "server_vad"}` defaults. During a hold/transfer, ring tone, line noise, or the tail of the agent's own audio is enough to cross the default VAD threshold and fire `input_audio_buffer.speech_started` on non-speech, which can trigger a new response while a real one is still in flight — that's consistent with two bot turns firing with nothing real from the agent between them, and with a response apparently reacting to audio before the transcript for that audio is fully in. This is the same client/server state-race family as the 2026-08-19 "barge-in gated on task-liveness" entry above, just showing up as a false trigger instead of a missed one.
- **Fix:** Explicit VAD tuning in `bridge/server.py`'s `session.update` call — `threshold: 0.6` (up from the implicit default, less sensitive to brief non-speech noise), `prefix_padding_ms: 300`, `silence_duration_ms: 600` (longer confirmed silence required before a turn is considered over). Also stopped logging `response_cancel_not_active` as an `OpenAI Realtime error` — confirmed it's an expected, harmless race (our local `response_active` flag says a response is in flight, OpenAI already finished it server-side before our cancel message arrived), not a real fault, and it was cluttering the logs on nearly every turn.
- **Status:** fix applied, not yet re-verified — needs another real test call, ideally another one that goes through a hold/transfer, to confirm the false-trigger double-turn doesn't recur and that turn transitions sound cleaner. The VAD threshold change is a reasonable first move but tuning phone-line VAD against real background noise/hold music often takes more than one pass.

### 2026-08-19 — Recording static traced to clipping in the audioop mix (not a real-time audio bug)
- **What happened:** Second real test call (CAcb4f1056f73fc5b2194b8a6771526317) still had reported static and "distant"-sounding voices even after the VAD tuning above. Checked the saved recording with `ffprobe`/`astats`: peak level -0.18 dB — effectively pinned at 0 dBFS, the signature of clipping.
- **Root cause:** `CallRecorder._mixed_pcm()` summed the agent and patient PCM tracks with `audioop.add()` at full volume, no headroom. `audioop.add` clips rather than wraps past 16-bit full scale, so any moment both tracks had real signal at once - frequent, given the crosstalk documented above - the sum exceeded full scale and clipped, heard as static/crackle. This is a recording/mixdown artifact only; it does not affect what either side actually heard live on the call, since the live relay never mixes the two directions.
- **Fix:** Attenuate both tracks to 50% (`audioop.mul(..., 0.5)`) before summing in `recorder.py` - mathematically guarantees the mix can never exceed full scale even if both sides peak simultaneously.
- **Also noted, not yet fixed:** this same transcript has the bot's "Okay, thanks for transferring me. I'll wait to speak with the office/provider." logged twice in a row, verbatim - a second instance of the false-trigger double-response pattern the VAD tuning was meant to address. The tuning helped some (this call had one duplicate instead of two dissimilar back-to-back replies like the previous call) but didn't eliminate it. Worth another pass - possibly debouncing new responses while a previous one's speech is still being synthesized/played, not just relying on VAD thresholds.
- **Status:** clipping fix applied, not yet re-verified on a real call. The false-trigger double-response issue remains open.

### 2026-08-19 — Real fix for the false-trigger double response: stop letting OpenAI auto-reply to VAD alone
- **What happened:** The VAD threshold tuning (first entry, 2026-08-19) reduced but didn't eliminate the false double-response bug - the next real call still produced one exact duplicate bot line back-to-back. Tuning thresholds was treating the symptom (how sensitive VAD is) rather than the actual cause (OpenAI auto-generating a reply on *any* VAD-detected turn boundary, real speech or not).
- **Root cause:** `turn_detection` defaults to `create_response: true`, meaning OpenAI fires a full response the instant its own VAD thinks a turn ended - no requirement that the audio actually transcribed to anything meaningful. Hold tones, ring noise, and line static all cross the VAD threshold under real phone conditions. Separately, the bot's own `response_active` flag cleared the instant text generation finished, not when its ElevenLabs audio actually finished *playing* on the call (which takes the real length of the utterance) - so a stray sound during that playback window looked, to our code, like a totally free turn.
- **Fix:** Two changes in `bridge/server.py`. (1) `create_response: false` in `turn_detection` - OpenAI now only transcribes and waits; we call `response.create` ourselves, and only when `conversation.item.input_audio_transcription.completed` carries real non-empty text. (2) `_speak()` now computes actual playback duration from bytes sent (mulaw 8kHz = 8000 bytes/sec) and records `call_state["speaking_until"]`; a transcription completing before that timestamp is treated as noise caught mid-utterance and doesn't trigger a reply.
- **Status:** fix applied, not yet verified on a real call - this is the intended real fix (addressing why responses fired, not just how sensitive the trigger was), but phone-line audio is messy enough that it's worth confirming on an actual test call before trusting it, per this file's own pattern of not assuming a fix worked without re-testing.

### 2026-08-19 — Manual response.create fix had its own bug: two replies' text merging into one garbled line
- **What happened:** First real call after the previous entry's fix (create_response: False + manual triggering) still didn't sound like real dialogue - the bot's opening line was two unrelated sentences run together with no space: "...then I'll wait for your guidance.Hi, this is Tyler Brooks...". Read out loud, this is what "sounds like it's reading a script" instead of holding a conversation.
- **Root cause:** The new manual-trigger code checked `speaking_until` before calling `response.create`, but never checked whether a response was *already being generated*. Whisper commonly splits one utterance into multiple transcription segments; each `conversation.item.input_audio_transcription.completed` event called `response.create` independently, with nothing to stop two from firing close together. Both responses' `response.output_text.delta` events land in the same shared `text_buffer` with no per-response id separation, so their text interleaves and gets flushed as one line whenever either one's `response.done` arrives first.
- **Fix:** Added a `response_active` guard before firing `response.create`, and (since dropping a segment that arrives while busy would silently lose real content) a `pending_reply` flag that gets deferred instead of discarded - fired from `response.done` if we were mid-generation, or from a small watcher task (`_fire_pending_reply_when_ready`) if we were just mid-playback of our own line. `response_active` is now also set immediately (optimistically) the moment we send `response.create`, not just when OpenAI's `response.created` echoes back - closes the same race for a third time (send -> await echo was itself a window another transcription event could slip through).
- **Status:** fix applied, not yet re-verified on a real call. This is the third pass at this same class of bug (state-tracking races between our local flags and OpenAI's actual server state) - each one has been real progress, not just moving the symptom, but this architecture inherently has a lot of these races and it's worth treating "still garbled after this fix" as a real possibility on the next call, not a surprise.

### 2026-08-19 — Bot talked over the agent's real greeting, replying to the recorded-call disclaimer instead
- **What happened:** Heard live on the next call: the bot started talking almost immediately, cutting into the agent's actual greeting. The transcript confirms it - the bot's first line landed right after "This call may be recorded for quality and training purposes. Para español, oprima el 2," a full turn *before* the agent's real "Thanks for calling Pivot Point Orthopedics... How may I help you today?" ever gets transcribed.
- **Root cause:** The manual response-triggering logic (added earlier today) replies to the first non-empty transcription it sees, with no concept of "this is boilerplate, not a real conversational turn." The recorded disclaimer and language-selection menu are exactly the kind of content that transcribes as real, complete-sounding speech, so nothing in the code distinguished it from an actual greeting worth responding to.
- **Fix:** Added a 5-second grace period from call start (`call_state["greeting_grace_period_ends"]`) during which no reply is allowed to fire, real content or not - deferred through the same watcher mechanism used for "still speaking," so nothing is lost, just delayed until the intro has had time to finish.
- **Status:** fix applied, not yet re-verified. 5 seconds is a guess calibrated to this specific test line's disclaimer + language-menu length, not derived from anything - worth watching whether it's too short (still clips the greeting) or too long (bot now waits noticeably after a real quick greeting) on the next call.

### 2026-08-19 — Added timestamped event logging to separate our latency from PGA's agent's latency
- **Context:** The CA0c3bf0060e10ecaef9b03b45cb800a77 recording had two long dead-air gaps (11s and ~19s) even though the transcript content itself was coherent for the first time. A plain transcript can't distinguish "our code took a while to reply" from "PGA's agent itself took a while to generate its response" - both look like silence in the recording.
- **Change:** Added a `_log()` helper printing `[t={elapsed}s] message` (elapsed since call start) at every point a response is requested or completes: PGA transcript ready, each of the three response.create call sites (immediate / deferred / watcher), and our own response text ready. Purely diagnostic, no behavior change.
- **Status:** in place for the next test call - the terminal output during that call, cross-referenced against the recording's silence gaps, should show whether the dead air sits between "PGA transcript ready" and "response.create sent" (our latency) or between "response.create sent" and "our response text ready" (OpenAI's latency) or neither (PGA's own agent being slow to speak in the first place).

### 2026-08-19 — Replaced the flat 5-second greeting timer with a real debounce
- **What happened:** Called out (correctly) that a fixed 5-second grace period before the bot's first reply doesn't mean the bot is actually *listening* for the greeting to end - it's a guess calibrated to one specific disclaimer's length, with no relationship to what's actually being said. Too short and it still clips a longer intro; too long and it makes the bot pause oddly after a short one.
- **Fix:** Replaced the timer with a debounce. Every `conversation.item.input_audio_transcription.completed` event bumps a generation counter and schedules a `DEBOUNCE_SECONDS` (1.2s) wait; if another segment arrives before that wait elapses, the counter moves again and the earlier wait bows out. A reply only actually fires once nothing new has come in for a real 1.2s - i.e. once the other side has genuinely stopped talking, whether that took 2 seconds or 15. This also subsumed the earlier "still speaking" and "response already generating" deferred-reply logic into one function (`_maybe_respond`), replacing three separate call sites for `response.create` with one.
- **Status:** fix applied, not yet re-verified. This should generalize better than either the immediate-fire behavior or the flat timer, but debounce length (1.2s) is itself a guess and may need tuning - too short and the segment-splitting problem could resurface, too long and it'll feel sluggish on quick exchanges.

### 2026-08-19 — Debounce alone wasn't enough for the opening disclaimer
- **What happened:** Next call still had the bot replying to "Esta llamada puede ser grabada..." before the real "Thanks for calling Pivot Point Orthopedics..." greeting - the exact same symptom as the flat-timer version, just with the debounce fix in place instead.
- **Root cause:** The 1.2s debounce is a reasonable gap for mid-conversation turns, but the real gap between the call-start disclaimer/language-menu ending and the live greeting starting is apparently longer than 1.2s - so the debounce correctly (by its own logic) decided the disclaimer was a complete, reply-worthy turn. Debounce and "don't reply to boilerplate" are two different problems; fixing one doesn't fix the other.
- **Fix:** Kept the debounce for all turns, but made the bot's first-ever reply of the call specifically wait out a longer 4.0s debounce (`FIRST_TURN_DEBOUNCE_SECONDS`) instead of the normal 1.2s - long enough to bridge a typical disclaimer-to-greeting gap without falling back to a flat pre-reply mute like the earlier, less content-aware version.
- **Also noticed, not yet explained:** this transcript has a stray `[PGA AGENT] Bye.` line in the middle of the identity-verification back-and-forth, with more agent lines continuing normally right after. Likely a Whisper transcription artifact on noise/crosstalk rather than PGA's agent actually saying goodbye mid-conversation, but worth watching for on the next call rather than assuming.
- **Status:** fix applied, not yet re-verified. Also: this recording has two more long silence gaps (~22s and ~11s) - the timestamped `_log()` output from this same call (not yet reviewed) should say whether those are our own latency or PGA's agent taking a while to respond.

# Architecture

_Kept from day one so decisions are recorded when they're made, not reconstructed after the fact. The system below reflects the current, working state; the full history of how it got here — including two earlier architectures and why each was replaced — is in the Decision Log below. Read this top section for "what it is today," the Decision Log for "why it looks like this."_

## How it works (current)

`place_call.py` validates the requested scenario (fail-fast: a bad scenario id or voice id never reaches a real phone call), then calls ElevenLabs' Conversational AI platform's Twilio outbound-call endpoint with a per-call `conversation_config_override` carrying that scenario's system prompt (`scenarios/loader.py`'s `build_instructions()`), voice id, and TTS speed. ElevenLabs' platform places the call through the project's Twilio number and runs the entire conversation itself — audio in, GPT-4o reasoning, TTS out, turn-taking, VAD, barge-in, and recording, all handled platform-side. There is no local server and no public webhook: the whole call is one outbound API request.

Once the call ends, `fetch_conversation.py` polls ElevenLabs' conversations API for that `conversation_id`, then writes `recordings/{callSid}.mp3` and `transcripts/{callSid}.txt` in the same `[SPEAKER] text` transcript format the project has used from the start. `place_call.py` calls this automatically unless run with `--no-wait`.

A one-time `setup_agent.py` creates the ElevenLabs agent (GPT-4o as the reasoning LLM, `ulaw_8000` telephone audio both ways, an empty first message so the agent waits out PGA's disclaimer/greeting instead of speaking first) and imports the project's Twilio number so ElevenLabs can place calls from it directly.

## Why this architecture won

Twilio is still the telephony carrier — Media Streams / outbound calling remains the simplest way to get a real PSTN call from Python, and that choice never changed across all three architectures this project went through. What changed is who owns the conversation itself. The project started with OpenAI's Realtime API doing speech-to-speech reasoning end-to-end, moved to a split where OpenAI reasoned in text and ElevenLabs handled voice, and ended up on ElevenLabs Agents (GPT-4o as the reasoning LLM, ElevenLabs owning the live call). Each step is logged in detail below; the short version is that PGA's #1 evaluation criterion — a coherent, natural voice conversation — is exactly what hand-built turn-taking code kept failing at, repeatedly, under real phone-line conditions. Moving that responsibility onto a platform that owns it natively fixed the failure class rather than the next instance of it.

**Being direct about what this is and isn't:** the current architecture is a cascaded pipeline (audio → speech-to-text → text reasoning → text-to-speech → audio), not true native speech-to-speech — OpenAI's Realtime API in audio-to-audio mode would have been that, at the cost of its ~10 fixed voices versus the 12+ distinct ElevenLabs voices this project's scenario suite needs. The real win from the final migration isn't "we achieved speech-to-speech" — it's that turn-taking, VAD, and barge-in are now a platform's solved problem instead of this project's hand-rolled, repeatedly-buggy code.

## Decision Log

_Running log of choices and tradeoffs, added to as the system is built — the goal is that ARCHITECTURE.md can be read on its own at submission time without reconstructing "why" from the code. Each entry: decision, alternatives considered, why this one won._

### 2026-08-18 — Realtime API over STT->LLM->TTS pipeline
- **Decision:** Use OpenAI's Realtime API (speech-to-speech) for the caller bot instead of a chained Whisper -> GPT -> TTS pipeline.
- **Alternatives considered:** Whisper (STT) -> GPT-4 (reasoning) -> ElevenLabs/OpenAI TTS pipeline. Gives more control per stage (inspectable transcript text, swappable voices) and is easier to log deterministically.
- **Why Realtime API won:** PGA's #1 evaluation criterion is a coherent, natural voice conversation — submissions that don't clear that bar are rejected before code review. A chained pipeline stacks latency at each hop (STT finish -> LLM finish -> TTS render) and needs hand-built voice-activity-detection and barge-in handling to feel natural. The Realtime API does turn-taking and interruption handling internally, at the cost of less fine-grained control over exact wording — an acceptable tradeoff since the bot's job is to *sound like* a real caller, not deliver scripted lines.

### 2026-08-18 — Twilio for telephony
- **Decision:** Twilio Media Streams to place the outbound call and get bidirectional live audio.
- **Alternatives considered:** Other telephony APIs (Vonage, SignalWire); a SIP trunk directly. Twilio was chosen for its maturity, simple Python SDK, and native WebSocket media streaming that plugs directly into a bridge server.
- **Tradeoff accepted:** requires a publicly reachable webhook (ngrok in dev) for Twilio to reach the bridge server — adds a moving part during local development that a production deploy wouldn't have.

### 2026-08-18 — Considered: Gemini Live API (already have access, no new account needed)
- **Question:** Since I already have Gemini API access, why not use Gemini Live API instead of setting up a new OpenAI account?
- **Finding:** Gemini Live API does not natively support g711/mulaw 8kHz audio (the format phone calls use) — this is a long-standing, unresolved request from developers (open since May 2025). Bridging it to Twilio requires hand-rolled audio resampling: 8kHz mulaw -> 16kHz PCM on input, and a two-step 24kHz -> 16kHz -> 8kHz downsample on output (done in two steps specifically to avoid audible aliasing artifacts from a single big jump). Developers report residual noise from the conversion. OpenAI's Realtime API accepts/returns g711_ulaw natively, so Twilio's raw audio passes straight through with no conversion code at all (see bridge/server.py).
- **Decision:** Still use OpenAI Realtime API. The avoided setup friction of reusing an existing Gemini key doesn't outweigh the real risk: added DSP code within a 6-hour build budget, and a documented risk of audio artifacts undermining PGA's #1 evaluation criterion (a coherent, natural phone conversation). Informal naturalness rankings put Gemini ahead of OpenAI, but that's a soft signal against a hard integration cost.
- **Revisit condition:** if OpenAI Realtime access or billing setup becomes a blocker, Gemini Live is the documented fallback, with the resampling work above scoped in advance rather than discovered mid-build.

### 2026-08-18 — ngrok for local development, not a production choice
- **Problem:** Twilio's servers need a public URL to fetch call instructions (`/twiml`) and open the live audio WebSocket (`/media-stream`). The bridge server runs on `localhost:8000` during development, which isn't reachable from the public internet.
- **Options considered:** (1) ngrok - a local tunnel that maps a public URL to `localhost:8000`. (2) Deploy the bridge server to a real host (cloud VM, etc.) with a real public address before running any test calls.
- **Decision:** Use ngrok for development/testing. It requires zero infrastructure setup, matches the challenge's actual scope (running test calls from a laptop, not standing up production hosting), and is the standard, fastest way to get a Twilio webhook working locally.
- **Tradeoff accepted:** the ngrok URL changes every time it's restarted (on the free tier), so `PUBLIC_BASE_URL` in `.env` has to be updated each dev session before placing calls. Not a concern for this project's scope - a real deployment would use a fixed hostname instead and wouldn't need ngrok at all.

### 2026-08-18 — Recording + transcript capture: mix to one file via audioop, convert with ffmpeg
- **Problem:** PGA requires a recording (OGG/MP3) and transcript for every call, with both sides of the conversation. The live relay already moves mulaw audio in both directions; recording just means also keeping a copy of it and turning it into a real audio file at the end of the call.
- **Decision:** Buffer both directions' raw mulaw bytes in memory during the call (call volume is small - short test calls - so no need for streaming-to-disk complexity). At call end, decode both to linear PCM and mix them into a single track with `audioop.add()`, write a WAV (stdlib `wave`, always available, no extra dependency), then shell out to `ffmpeg` to convert to MP3 (the format PGA requires).
- **Note on `audioop`:** Python removed `audioop` from the standard library in 3.13. Used the community-maintained `audioop-lts` backport as a fallback import so this doesn't silently break on newer Python - see `bridge/recorder.py`.
- **Tradeoff accepted:** the MP3 conversion depends on `ffmpeg` being installed locally. Chose to degrade gracefully (keep the WAV and print a clear warning) rather than crash a whole call's recording over a missing external tool, but this does mean `ffmpeg` needs to be installed before a real submission-ready MP3 comes out.
- **Transcript source:** OpenAI's Realtime API transcribes both directions for us - `response.output_audio_transcript.delta` for our own patient bot's speech, and `conversation.item.input_audio_transcription.completed` (via `session.audio.input.transcription`, enabled in the session config) for PGA's agent's speech. No separate transcription service needed.

### 2026-08-19 — ElevenLabs becomes the voice; OpenAI Realtime stays the ears and brain
- **Decision:** Split the bot's brain in two. OpenAI's Realtime API keeps doing everything except speaking — it still hears the raw mulaw call audio, still does server-side turn detection, still holds the conversation state, still decides what the patient says next — but its `output_modalities` is now `["text"]`, and the reply text is synthesized by ElevenLabs streaming TTS (`bridge/tts.py`, model `eleven_flash_v2_5`, `output_format=ulaw_8000`) and streamed into the call. This supersedes the *output half* of the 2026-08-18 "Realtime API over STT->LLM->TTS" entry; the input/reasoning half of that decision stands.
- **Why:** more natural-sounding voices, plus variety. OpenAI Realtime's 10 fixed voices are functional but noticeably synthetic once they're on an 8kHz phone line; ElevenLabs' models render more convincingly as an actual human caller even after that same downsample. Variety was the other half of it — the scenario suite wants 12+ callers who sound like genuinely different people (an 84-year-old man, a harried daughter, a chronic interrupter), which a 10-voice fixed set can't cover but ElevenLabs' voice library plus per-scenario `voice`/`voice_direction` fields can. Each scenario now pins a distinct voice id in `scenarios/*.json`.
- **Alternative considered — full swap to ElevenLabs Conversational AI (their agent platform):** researched first, and their agent WebSocket does accept `ulaw_8000` both ways, so the resampling objection that killed Gemini Live doesn't apply. Rejected anyway: it replaces the reasoning engine too (new prompt/override plumbing, agent pre-configuration in their dashboard, per-field security toggles), all to solve what is purely a voice problem. Swapping only the mouth keeps the working turn-taking/reasoning stack untouched.
- **Alternative considered — the full chained pipeline (transcription-only Realtime session + separate Chat Completions reasoning call + TTS):** rejected for latency and moving parts. It adds a second model round trip per turn and hand-built conversation-history tracking, and its only advantage (per-stage inspectability) isn't worth reintroducing the exact "latency at each hop" problem the 2026-08-18 entry chose Realtime to avoid. The text-modality approach keeps VAD, turn-taking, and state in the one place they already work. (LiveKit's OpenAI plugin documents this same text-modality-plus-TTS pattern.)
- **What was measured before wiring (2026-08-19, real API):** `ulaw_8000` output verified byte-for-byte (bytes/8000 = seconds of speech, mixed and played back cleanly through recorder.py). Warm time-to-first-byte, median of 4 interleaved runs: **flash_v2_5 278ms, turbo_v2_5 338ms**. Cold first request: **1430ms** — connection setup, not model time — which is why `bridge/tts.py` holds one warm `httpx` client per process and `warm_up()` fires at call start. ElevenLabs streams ~12x faster than realtime playback.
- **Tradeoffs accepted:** (1) ~280ms of added dead air per turn vs. speech-to-speech — the price of the voice swap; judged acceptable against normal human phone-pause rhythm, to be re-checked on real calls. (2) Barge-in is now hand-built (the Realtime API did it internally): on `input_audio_buffer.speech_started` the bridge cancels TTS playback and sends Twilio a `clear`. The `clear` is sent *unconditionally* — because ElevenLabs outruns playback ~12x, a whole reply sits in Twilio's buffer long after the sending task finishes, so "is the playback task alive" says nothing about whether audio is still coming out of the phone (this exact bug was caught in the offline harness before any live call — see ITERATION_LOG.md). (3) The bot's own transcript is now the reasoning text logged *before* synthesis rather than a transcription of what was actually played — strictly more accurate, except that a barged-in line is logged in full even though the caller heard it cut off.

### 2026-08-19 — Moved the whole live call onto ElevenLabs Agents; retired the self-hosted bridge
- **Decision:** The call now runs end-to-end on ElevenLabs' Agents platform. `place_call.py` hits their Twilio outbound-call endpoint with a per-call `conversation_config_override` (the scenario's `build_instructions()` as the system prompt, the scenario's voice id as the voice); their hosted agent — GPT-4o as the reasoning LLM, configured by `setup_agent.py` with `ulaw_8000` audio both ways and an empty first message so it waits out PGA's disclaimer/greeting — holds the conversation; their platform records it. A new `fetch_conversation.py` polls the conversation after the call and writes `recordings/{callSid}.mp3` + `transcripts/{callSid}.txt` in the same `[SPEAKER] text` shape the old `CallRecorder` produced. The entire live bridge (`bridge/server.py`, `bridge/tts.py`, `bridge/recorder.py`, FastAPI, ngrok, `PUBLIC_BASE_URL`) is retired to `_to_delete/bridge-retired-2026-08-19/`.
- **Why:** the hand-built turn-taking layer was the project's dominant source of bugs. Eight `ITERATION_LOG.md` entries dated 2026-08-19 are all the same underlying problem — client-side state flags racing OpenAI's server state under real phone-line conditions (false VAD triggers on hold tones, double responses, two replies' text merging into one garbled line, replying to the recorded disclaimer instead of the real greeting, barge-in that silently never fired). Each fix was real progress and each next call found the next race. Turn-taking, VAD, and barge-in are exactly what a conversational platform owns natively; moving there deletes the whole bug class rather than patching its instances — along with every line of debounce, grace-period, `speaking_until`, and `pending_reply` code those entries added.
- **What was given up:** the OpenAI Realtime integration entirely (both the earlier speech-to-speech setup and the text-modality variant), the per-hop control that came with owning the bridge, and the local recording pipeline — recordings are now whatever ElevenLabs' platform captures, fetched after the fact instead of taped off the wire. `OPENAI_API_KEY` leaves `.env`; GPT-4o is still the reasoning model, but ElevenLabs calls it under their own credentials (spot-check the ElevenLabs usage dashboard after the first calls to see how conversational-minute billing lands). One platform constraint surfaced during setup and is logged here so it isn't re-discovered: English (`language: en`) agents must use `eleven_turbo_v2`/`eleven_flash_v2` — the v2_5 models the old TTS layer used are rejected for `en` agents at agent-creation time.
- **What was kept:** the scenario system, unchanged — `loader.py`'s `build_instructions()` and `get_voice()` plug directly into the override structure, and all 12 scenario JSONs work as-is. The fail-fast rule also survives: a bad scenario id or voice id still dies in `place_call.py` before anything dials. Per-call overrides are disabled by default on ElevenLabs' side for security; `setup_agent.py` enables exactly two (`agent.prompt.prompt`, `tts.voice_id`) and nothing else.
- **Continuity note:** the three calls recorded under the old architecture stay in `recordings/`/`transcripts/` as historical record; new calls count toward the submission's minimum going forward. File naming continuity: new files are keyed by Twilio call SID (same `CA...` stems as before) when the outbound-call response provides one, falling back to the ElevenLabs conversation id.
- **Major decision — infrastructure eliminated, not just simplified:** this migration removes ngrok and `PUBLIC_BASE_URL` entirely, not just from `.env` but from the workflow itself. The old architecture required three things running simultaneously for any call to work: an ngrok tunnel, the FastAPI bridge server, and `place_call.py` — and the ngrok URL rotated on every restart (free tier), so `PUBLIC_BASE_URL` had to be re-pasted into `.env` each dev session before a call could even be attempted (see the 2026-08-18 "ngrok for local development" entry). There is no public webhook target anymore because there is no local server for Twilio to reach — ElevenLabs' platform places and hosts the call directly. Running a test call is now one command, in one terminal tab: `python place_call.py --scenario <id>`. This is a direct, checkable consequence of the decision above, not a separate change — called out on its own because it's the single biggest day-to-day workflow win from the migration and easy to undersell as a footnote.

### 2026-08-19 — Per-scenario TTS playback speed
- **Decision:** Scenario JSONs may set an optional `"speed"` (0.7–1.2, default 1.0), passed through the same per-call TTS override as the voice id — `slow_processing_elderly_caller` runs at 0.85, `interrupting_caller` at 1.1. `voice_direction` prompt text shapes wording and cadence, but only an actual TTS-rate change makes the synthesized voice physically slower or faster.
- **Gotcha worth recording:** in ElevenLabs' agent override schema, `speed` is a top-level sibling of `voice_id` on the TTS override (verified against SDK models `TtsConversationalConfigOverride[Config]`), not nested under a `voice_settings` object as their plain TTS endpoints suggest. The override also had to be enabled account-side; done via `agents.update` PATCH on the live agent (readback-confirmed) rather than recreating the agent or clicking through the dashboard — `setup_agent.py` updated to match for any future recreation.
- **Guard:** `loader.get_speed()` validates range and type at load time, so a bad speed fails before dialing, same as a bad voice id.
